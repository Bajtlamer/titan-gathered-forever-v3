# Titan Gathered Forever

Titan Gathered Forever helps World of Warcraft Forever crafters understand their materials: what an item is used for, how much they have, where it comes from, and what their own observations say about obtaining it.

The long-term goal is a useful lifetime record for every item supported by the profession catalogues. This includes looting, mining, herbalism, skinning, fishing, disenchanting, crafting and cooking. Statistics should help players plan professions, compare sources, share results and perform later analysis.

Website: [titan-gathered.com](https://www.titan-gathered.com/).

## What the percentages mean

TGF v3 distinguishes **items obtained**, **successful outcomes**, **complete observed source samples**, and **observed profession actions**.

For example, a gem obtained from 3 of 20 complete observed mining sources has an observed acquisition rate of **15% (3 / 20)**. Obtaining five gems in one source adds five items but only one successful outcome. This does not establish the server's guaranteed drop rate or the probability of success for an unobserved action.

Fishing percentages describe complete looted catches in a zone, including junk catches, rather than every cast. Ordinary loot groups comparable source entries, zones and instance contexts. Disenchanting groups input item IDs; unreadable identity is explicitly unknown. Partial or unreadable loot does not create a complete rate sample. Recording policies prevent materials of a newly installed profession addon from inheriting samples collected before it was installed. Combined rates sum eligible samples rather than averaging character percentages.

Lifetime history begins with acquisitions recorded in `0.4.0`. Earlier versions saved map locations and observation counts, which cannot reconstruct item quantities or drop-rate denominators. Purchases, trades, bank transfers and current bag contents are not treated as gathered items. Instance acquisitions may contribute to history, while instance and raid locations are excluded from map recording.

Profession actions use separate schema-1 storage. An attempt requires a readable cast identity and a recognized start, channel start, success, failure or interruption event. Duplicate events share one attempt. A mining, herbalism, skinning or disenchanting completion means spell success, regardless of loot quantity. Fishing spell success only launches the line; its completion requires a confirmed fishing-loot window, even if you leave the loot behind. Stops without a confirmed result, explicit failures, interruptions and unresolved observations are reported separately. A stop does not prove manual cancellation or failure.

Profession actions are shown in Statistics (below), as one row per gathering profession (and disenchanting) next to the crafted recipes, with the first recorded action time in the details of the row, current-character or combined counts, and profession filters. Combined coverage begins at the earliest included character observation; it does not mean all characters recorded continuously since then. Recording gaps are not reconstructed. Reloads, world transitions and action-recording changes seal pending observations without inventing outcomes. Recent cast receipts are bounded to 1024 per character; lifetime aggregates remain. These counters do not change source-rate percentages or reconstruct actions from earlier history.

Crafting/cooking production also uses separate schema-1 storage. It requires a readable player cast start while recording is enabled and live recipe metadata from the corresponding profession. Supported item recipes include Cooking, Alchemy, Blacksmithing, Engineering, First Aid, Leatherworking, Tailoring, smelting under Mining and item-producing Enchanting recipes that the client identifies as ordinary item recipes. Recraft, dummy, gathering, enchanting-application and salvage recipe flags are excluded. Unknown metadata or protected fields do not produce guessed records.

Statistics at the bottom of the game's Professions window shows what you did with your professions, in one panel with three views chosen in a combo box. The native recipe list is not changed: the number in square brackets there is what can be made with the materials at hand. The number of completed crafts of this character is the Completed column here, and the right click menu of a recipe shows it as "Crafted so far". **Attempts** lists the crafted recipes and, as one row each, the gathering professions (Mining, Herbalism, Skinning, Fishing) and disenchanting, with attempts, completed crafts or actions and the completed percentage; a click on a column header sorts by it and a second click reverses the order. Click a row for the details: failed, interrupted, stopped and unresolved attempts, output distributions, matched operations and observed bonus and multicraft rates for recipes (the client gave no values for the last three so far). Fishing completion means a catch window. **Materials** estimates usage from fixed required materials in tracked recipes. **Gathered items** has tabs: Overview (the summary of every gathering profession) and one tab for each installed gathering profession, which shows what it collected from complete loot windows, valued at the better of the vendor price and the auction price after the fee, sorted by quantity or by total value (click a header); click an item for its sources. The views can be filtered by profession and character (Gathered items by tab), and `/tgf production` (or `/tgf actions`) opens Statistics directly. A click on any profession tab closes the panel.

Production result events have no recipe ID. Matching therefore requires an unambiguous recent output/recipe context and a positive operation identity, within 60 seconds of the cast start. Secondary outputs arriving before a primary binding, first-craft rewards, unpaired results and ambiguous recipes are skipped. After a recording gap, recent sealed casts can suppress new output attribution for the remainder of that window while completed casts remain counted. Reloads preserve aggregates and seal pending contexts. Ordinary recipe identities used for recrafts and the actual Forever event sequence still require live validation. Lifetime material rows and item tooltips show crafted quantities separately from acquired loot; crafting creates no map spots or loot-rate samples.

## Install only what you need

Download the **complete collection ZIP**, or download the **core ZIP plus the individual profession ZIPs** you want. Every optional module requires both the core and Titan Panel. A profession ZIP does not include the core.

Extract ZIPs into the Forever client's `Interface/AddOns/` directory. The resulting folders must be siblings:

```text
AddOns/
  Titan/                       # Titan Panel, installed separately
  TitanGatheredForever/               # TGF v3 shared core
  TitanGatheredForever_Mining/        # Optional
  TitanGatheredForever_Herbalism/         # Optional Herbalism module
  TitanGatheredForever_Skinning/      # Optional
```

Available modules: Alchemy, Blacksmithing, Cooking, Enchanting, Engineering, First Aid, Fishing, Herbalism, Leatherworking, Mining, Skinning and Tailoring. Auction Items is an additional optional module. Disabled modules do not load their catalogue tables.

Install the renamed folders and disable the previous-generation addon folders. Do not enable both generations together. Enable the new Titan broker entry if Titan still displays the previous one.

## Preserve existing saved data after the rename

WoW names its account SavedVariables file after the core addon folder. Renaming the folder therefore requires a one-time migration to retain settings, inventory snapshots, spots and lifetime history.

Runtime ZIPs contain runtime files only. If you installed from ZIPs, first download the [migration tool](tools/migrate_savedvariables.py) from the source and adjust its script path in the command below.

1. Close WoW so its current data is saved, and back up the account's SavedVariables directory.
2. From the source checkout, run the migration tool, using the old and new files in that same account directory:

```sh
python3 tools/migrate_savedvariables.py \
  "/path/to/WTF/Account/ACCOUNT/SavedVariables/TitanGathered2.lua" \
  "/path/to/WTF/Account/ACCOUNT/SavedVariables/TitanGatheredForever.lua"
```

The tool changes the old `TitanGathered2ForeverDB` assignment to `TitanGatheredForeverV3DB`, preserving the table contents and original file. It refuses to overwrite existing new data. Repeat for each account whose data you want to retain. This is data migration, not compatibility with another WoW edition.


## Use TGF v3

Right-click the Titan entry for Display, Professions, Additional items, Icon appearance, Flight points, Trainers and recipe vendors, Gathering map, History and sources, and Diagnostics settings. Data collection is always on: history, map spots, profession actions, production, PvP, rare loot and trainer and vendor windows are recorded whatever the settings say, and only disabling an addon in the AddOns list stops it. Settings only decide what is shown. Map spots are not recorded inside instances, but the statistics there are.

Everything that needs no parameter is in the right-click menu of the Titan entry:

- Display: Show minimap button, Next summary page and Previous summary page. The round minimap button opens the unlearned recipes window with a left click, the menu with a right click, and can be dragged around the minimap edge.
- Icon appearance: the small icon appearance window.
- Trainers and recipe vendors: map toggles, profession filter, Unlearned recipes, Trainers (list of trainers), and Pin placement (find the nearest pin, swap map axes if pins look mirrored).
- History and sources: Lifetime materials, Observed chances, Profession statistics, Economy, PvP Board, Export statistics.
- Diagnostics: Debug mode, Also show debug messages in chat, Clear debug log, Refresh inventory, Show status report and Show NPC recording log (why the last trainer or merchant windows did or did not record, with raw client answers). Debug mode writes important events (casts, loot, trainer and merchant windows, profession windows, bank and world changes, honor events), status messages and recording outcomes to a bounded debug log of the latest 1,000 lines. The log lives in the saved variables file, which the client writes on /reload and logout, so debug messages no longer fill the chat unless Also show debug messages in chat is on.

A command is only needed when it takes a parameter:

- `/tgf recipe <recipeID> [operations]`: reagent plan for a recipe; omit the ID after selecting a native profession recipe. Plan selected recipe reagents in the menu does the same for the selected recipe.

The earlier parameterless commands (`/tgf settings`, `icons`, `history`, `chances`, `actions`, `production`, `pvp`, `recipes`, `export`, `refresh`, `status`, `next`, `prev`, `npc`, `npc swap`) still work as shortcuts but are no longer documented, because the menu covers them.

Click a material in a report for its recorded sources. Use **TGF v3 spots** on the world map to clear a category from the displayed map after confirmation. Debug mode prints local diagnostics and is normally off.

Profession actions are recorded for every installed profession addon, independently of lifetime item history and map visibility. Turning a profession off in the Professions menu only hides it from the reports; its counts keep growing and show again when it is turned back on.

Crafting and cooking production is recorded for every installed profession addon. Turning a profession off in the Professions menu or hiding the map does not stop production recording; it only hides the profession from the reports.

## Trainers and recipe vendors

Trainers and Recipe vendors are separate map switches in the menu, with a per-profession filter, and they work on the world map and minimap without the gathering map. Pins start from a bundled Classic seed and show as not yet confirmed in game until you open that NPC's window, which records its recipes, required skill and price. Observed data replaces seed data, and unknown values stay unknown. Vendor and trainer tooltips show the NPC name in gold, role and confirmation state in gray (green when confirmed in game), a rule, then one white line per recipe with the required skill in brackets after the name and only the price on the right in the classic gold, silver and copper icon format. Recipes you know are marked once that profession window has been opened. The Unlearned recipes window lists recipes you have not learned and shows whether a trainer or only a vendor provides them. It scrolls with the mouse wheel or a scroll bar, shows recipes that need more skill than you have in red (so the ones you could learn now stand out), has a profession filter, shows NPC names in green, and hovering an NPC name shows every source of that recipe with its zone, coordinates and price. Clicking a row opens the map at the zone of the first source and marks every trainer or vendor of that recipe with a pulsing red ring on the world map and minimap, even when the map filters would hide them. The rings belong to the map opened from the window: closing the world map removes them, and so does clicking the same row again, choosing another recipe or waiting five minutes. Reopening the map normally shows no rings. The Trainers tab lists every profession trainer with its zone, coordinates and status (Not visited, or Visited with the date the trainer window was recorded). It starts with the trainers not visited yet, can show visited or all trainers, filters by profession, searches by name, profession or zone, shows what a trainer teaches on hover, and opens the map with a red ring on the trainer when a row is clicked. Pins never appear in instances.

## Plan recipe materials

Select a recipe in the profession UI, then use `/tgf recipe` or Plan selected recipe reagents in the Titan menu. The profession window of the client has a Reagents button in its header, left of the maximize button (left of the close button when that is hidden), that opens the reagent window for the selected recipe with the number of crafts typed beside Create, and closes it when it shows that recipe already (like the minimap button). A right click on a learned recipe in the recipe list also has a Reagents entry that opens that recipe. You can also enter an explicit recipe spell ID and operation target, such as `/tgf recipe 2536 3`. Production recipe details and known recipe examples in material source menus link to the same planner. The window lists one reagent per line with the amount needed, the amount in the bags and in the bank, what is missing and where to get it. Green is ready (enough in the bags), yellow is enough but in the bank (the last column says how many to take), red is missing (the last column names a merchant that was seen selling it with the price each and the zone, otherwise the best observed source, or says there is none). Merchants are recorded when their window opens, only for goods that belong to the professions, and the source menu of a reagent lists them (a click opens the map and marks the merchant). The Auction each column and a line above the list give the lowest buyout per unit from the last auction scan and what the missing reagents would cost there.

Crafting profit: a tab (Titan menu > History and sources > Crafting profit, or the tab strip) lists the recipes of the recipe book with the cost of the materials, the product sold to a vendor or on the auction house after its fee, where it sells better and the profit of one craft, the best first. The recipes come from the recipe books of the profession addons: each addon carries the recipes of its own profession (product, materials; generated into its Data.lua by tools/generate_catalog.py from catalogue/forever-recipes.json and the verified supplements, a mirror of client tables for 1.60.1 that is not complete), so a player who installed only some profession addons loads, prices and lists only those professions. "My recipes" lists the recipes the character has learned (by recipe ID where the profession window gave the IDs, otherwise by name; a profession must have been read once), "All recipes" lists everything; a profession filter and a search narrow it. Green is a profit, red a loss, gray is unknown because a price is missing, and a star means one item per craft is assumed until the recipe was opened in the reagent window, which keeps the real number. When a profession window is read, the schematic of every recipe of the profession is read in small steps: the number a craft makes is kept (the star disappears), and a recipe that the recipe table lacks is kept with its product and materials and listed too (a footer line says how many). An Auctions column gives the number of auctions behind the price of the product; fewer than three (shown in orange) is a thin market, where one odd offer sets the lowest buyout, so such recipes are hidden by default (the Markets filter: 3+ auctions or All markets; a product that sells better to a vendor is never hidden). The reagent window marks a price that rests on fewer than three auctions the same way. A click opens the reagents of the recipe.

Modular data: the addon is built to run with any set of profession addons. The reagents, the recipes and their products, the auction prices and the trainers, recipe merchants and pins all follow the installed and switched-on professions (Titan menu > Professions) and nothing else: the auction scan reads the whole list because the client gives no filter, but it keeps only the reagents of the installed professions and the products of their recipes; trainers and recipe merchants of a profession whose addon is missing are not recorded, listed or pinned; the profession filters list the installed professions only. The saved recipes (recipeMakes, recipeExtra) come only from installed professions. What is not modular yet: the seed of trainers and vendors (Data/NpcSeed.lua, about 190 KB) still lives in the core and is filtered when it is used, not when it is loaded.

Windows are opaque and a click raises a window above the others, so a window opened over another does not show it through. The profession window and the auction house window of the client can be moved too: drag an empty place of the window, and the position is kept like the others (Titan menu > Display > Let me move the profession and auction house windows switches this off). Window positions: every window (the tabbed window, the reagent window, the export window and the icon appearance window) opens where it was left, also after /reload and a restart; Titan menu > Display > Reset window positions puts them back in the middle of the screen.

Auction prices: with the auction house open, the Scan prices button below its window (or Titan menu > Auction prices > Scan now) reads the whole auction house once with the client's full scan, which the client allows about every 15 minutes, and keeps the lowest buyout per unit, the quantity and the number of auctions of every item of the profession catalogue (bid-only auctions are ignored). The list is read in small steps so the game does not stall, and a progress bar beside the button shows the phase (waiting for the auction house, then the percentage and the number of auctions read); the chat gets a line when the list arrives, at every quarter of a long list and at the end. The scan keeps the lowest buyout of every item on the auction house (the items of the profession catalogue with quantity and auction count, all other items, which includes the products of recipes, in one packed number each). The reagent window shows the product of the recipe: where one unit sells for more (the vendor price against the lowest buyout after the 5% auction fee, which is an assumption and not read from the client), the prices, and the profit of one craft (and of the planned crafts) against the materials at the cheapest known price (auction or a merchant that was seen selling it); an unknown price makes the profit unknown, never a guess. The window is as tall as its list. The item tooltip shows the scanned price of any item that has one (the items of the profession catalogue and everything else, switchable in Titan menu > Auction prices), what the items you hold are worth, what a vendor pays and which of the two leaves more, and how many auctions and how old the scan is. For the items of the profession catalogue (the lowest buyout each, what the items in your bags and bank are worth at it, and how many auctions and how old the scan is). The prices are kept per realm and the menu can scan automatically when the auction house opens (at most every 30 minutes, off by default) or clear them. Missing reagents are listed first. The - and + buttons and the number box set the planned crafts (Shift adds or removes five); Refresh requests the normal inventory refresh. Planning does not craft or reserve anything.

Buyout undercut: in the Sell tab of the auction house a row in the left panel, above the Buyout Mode check box, has a combo box (2, 5, 10 or 15 percent) for the percentage, followed by what a sale brings after the fee ("AH sold") and what a vendor pays for the same stack ("Vendor"). When you pick an item to sell, the add-on searches the auction house for that item and fills the Buyout price with the lowest existing buyout (per unit for stackable goods) minus the chosen percentage. Your own auctions are ignored, a percentage that would put a sale, after the auction house fee, below what a vendor pays sets the Buyout to the lowest price that still beats a vendor and says so in red, nothing is set when there is no other auction, and a price you type yourself is not overwritten for that item (choosing another percentage prices the selected item again). It can be switched off in Titan menu > Auction prices. It needs a live search per item, so it is subject to the throttle of the auction house; the last fills are recorded in the saved variables (auctionUndercutLog). The Current listing section in the left Market history panel shows, when the posting beats a vendor (or no vendor price is known), what it earns when the item sells (the price after the 5 percent auction fee; the deposit comes back with it), the comparison with selling the same units to a vendor, what a failed auction loses (the deposit) and the number of units that must sell for the gain over the vendor to cover the deposit ("the item must sell" for a single item); when even a full sale gains less than the deposit, a red "Not worth the risk" warning replaces that number. When the vendor pays the same or more, only the red "Vendor pays more" comparison and the loss of a failed auction are shown, because what the sale would bring is of no use then. It does not compare the price with other auctions, a cost or your earlier sales. The deposit is read from the client; the fee rate and the loss of the deposit on expiry are assumptions that are still to be confirmed with a real sale.

Sales ledger: when you open a mailbox, the add-on reads the inbox (nothing is taken, opened or changed) and records every "Auction successful" mail that holds money once in the saved variables (sales): item, stack size from the invoice when available or from the subject, the money received, and the price, deposit, fee and buyer when the client gives the invoice (it may do so only after the mail has been opened; what is not given stays unknown). The sale time is estimated from the days the mail has left. `/tgf sales` lists the count and the newest sales. A bounded diagnostic log (mailLog) is written by the game events themselves: every reading of the inbox, a sample of other mails and the raw invoice values, so the client's values can be checked from the saved variables without any command.

Market history appears at the left of the auction house when an item is selected in Sell. Hide history saves the collapsed preference. Show history sits to the right of the Create Auction tab. If the window is too close to the left edge to dock the panel, Show history opens it over the left side of Sell. The panel shows the last scanned unit buyout with its date. The chart shows the player's own confirmed sales of the item over the last 30 days as soon as there is one sale day with a verified net price (each point divides the day's net proceeds by the verified number of units sold); the day with the highest net price is marked in green. Without a sale of the item the chart shows one point, the price of the last auction scan, because no history of scans is kept; without a scan, or when the item is not in the last scan, a short text says so. The sales section also shows the best sale: the highest net price per unit the player ever got for the item on this realm, with its date, kept in the saved data apart from the bounded mailbox ledger and never taken from other players' auctions. The sales section covers the last 30 days for the selected item ID, character and realm. It uses confirmed sales in the mailbox ledger, shows partial quantities as a lower bound, and uses actual invoice sale amounts and quantities for weighted unit averages. The net average excludes the returned deposit and uses invoices whose sale amount, fee and deposit add up to the money attached to the mail. Sale dates are estimates.

The Economy tab in the main window summarizes recorded merchant sales, auction sales, quest rewards and mob loot. The character selector defaults to All characters on the current realm and can show this character or another character with recorded history. Older auction records use the seller name, while the other sources use the character ID. A seller without a confirmed link to a character ID appears as a separate auction history choice. Merchant sales count new buyback entries when their combined price matches the money credited to the character. Buybacks are tracked separately as spending. Auction settlement shows gross sale amounts, fees, returned deposits and money attached to confirmed sale mails. The same ledger supplies Market history, and total income uses verified auction proceeds after fees and excludes returned deposits. Quest rewards use the cash amount reported by the client when a quest is turned in. Mob loot counts cleared coin slots from dead creatures when the credited money matches the amount shown in the loot window. The total is a lower bound based on the available records. Equipment repairs are recorded at merchants as spending (the wallet falls by exactly the fall of the cost of repairing everything) and shown as a running total and a count.

Native selection follows the highest learned rank used by the profession schematic; explicit recipe IDs remain exact. If a native rank transition cannot be resolved, select an explicit ID instead of receiving a guessed rank's requirements.

Reagent quantities come from live client schematics on demand. The planner aggregates repeated item requirements, shows available and missing quantities for the requested operations, and estimates the material limit. Display > Show bank counts selects Bags or Bags + Bank for both the planner and reagent context. Cached snapshots are labeled estimates with bank observation time where available. Unknown counts display zero and suppress the overall material limit. A material limit does not certify learned skill, tools, cooldowns, location or other crafting requirements; unlearned recipes are labeled.

Fixed single-item basic reagent slots are supported. Required alternatives, currency, variable quantities, protected data and unsupported slots leave the overall estimate unresolved; fixed rows may still be shown as a partial plan. Optional modifiers and finishing reagents are excluded. Recraft, gathering, salvage and dummy contexts are excluded. Ordinary enchantment recipes can be planned for their reagent requirements. Planning requires the recipe's loaded, enabled profession addon/category and does not load bulk recipe tables into the core.

Each reagent links to personal acquisition evidence and recorded map positions. Source suggestions prioritize larger observed samples; they do not establish the best place to farm. Source/zone rates and saved positions are distinct: a zone-wide observed rate is not a probability at a particular coordinate, and an old position does not establish current resource availability. Native reagent tooltips add only a short per-operation deficit and material-limit summary for the selected recipe. Live recipe selection, slot availability and planner layout remain under validation.

## Discovery data collection module

Titan Gathered Discovery (folder `TitanGatheredForever_Discovery`, version 0.1.0) is a diagnostic companion for the owner and for contributors who choose to help. It records what the WoW Forever client shows (loot and its sources, NPCs, vendors, trainers, quests, zones, professions, recipes), compares it with the data of Titan Gathered Forever and shows what is new or different, so that the catalogue can be completed on evidence. It is not a player feature, it is not part of the published collection and it requires Titan, the core and a restart after installing.

- Installing the module is the consent: recording starts by itself at the first login, with the notice printed once (`/tgfd` shows it again, `/tgfd stop` pauses and `/tgfd start` resumes; a pause is kept). The window has two tabs, the collected data and a guide to how the module works and how to hand the data over by Discord or e-mail; it opens with `/tgfd show`, from the Titan Panel entry "Titan Gathered Discovery" or from the right click menu of the minimap button. It never records chat, mail, gossip or quest text, player or pet names or GUIDs, and it does nothing with the auction house. Nothing is sent anywhere: contributors hand over a saved file themselves.
- Every long operation (`/tgfd compare`, `/tgfd scan recipes`, `/tgfd scan areas`, `/tgfd export`) starts only from a command, shows a progress window, can be cancelled with `/tgfd cancel` and stops on combat or a loading screen. `/tgfd show` opens the overview window and a read-only Titan Panel plugin shows the counts.
- `/tgfd export` checks for private values and stamps the data; after `/reload` the saved file can be sent. `tools/read_discovery.py` merges contributor files and compares them with `catalogue/` without running them. Nothing found is added to the catalogue automatically.
- Guides: [contributors](book-discovery-contributors.md), [data format and offline tool](ref-discovery-data-format.md), [plan and execution record](plans/plan-discovery-module.md), [release notes](release-notes/ref-discovery-0.1.0.md) and [CurseForge text](curseforge/ref-titan-gathered-forever-discovery.md).
- Packaging and installation: `python3 tools/package.py --standalone` and `python3 tools/install.py --addons-dir <path> --standalone-only [--apply]`.

## Export statistics

Use Export statistics under History and sources. The default is This character with names and GUIDs excluded. All characters retains per-character policy/coverage records plus a weighted combined summary. Include names/GUIDs is an explicit opt-in that resets on closing. Numeric game IDs, map IDs and gameplay timestamps remain in identity-excluded exports.

Select text, copy with Ctrl+C or Cmd+C and save UTF-8 JSON outside addon folders. The addon sends nothing. Its snapshot stays fixed while copying; Generate captures a new one. Small exports are complete schema-1 JSON. Large exports are numbered JSON parts: save every part from the same snapshot and reconstruct with `tools/read_export.py`. The reader rejects missing, duplicate, mixed or corrupt parts and refuses to overwrite files.

Exports preserve acquired/produced quantities separately, source policies and eligible denominators, action outcomes, production distributions and explicit proc-field counts. They exclude inventory snapshots, raw event receipts, coordinates and arbitrary saved labels. Unknown starts and unsupported feature schemas remain explicit. Exports are cumulative snapshots: do not sum repeated exports as independent observations.

See [ref-statistics-export-format.md](ref-statistics-export-format.md) for fields and reconstruction commands. JSON is the initial format because one flat CSV would lose policy/distribution relationships. Clipboard round trips remain a live-client validation gate.

## Development layout

The repository root contains the shared core and thirteen separate optional addon folders, plus the standalone TitanGatheredForever_Discovery folder (listed in `catalogue/standalone-modules.json`, outside the published set). All addon folders contain only game-required files. Development tools, tests, catalogue inputs, documentation and release notes live at the repository root. Generated packages are written to `dist/`; private local archives remain in ignored `.work/`.

`python3 tools/audit_catalog.py` reports evidence gaps without writes or downloads. Use `--check` for the generated report, `--mirror-file` for pinned mirror verification and `--client-tables` for offline build-labelled CSV verification. Audit/generation share input validation and protect report output from source-file aliases. Unresolved IDs and inherited associations remain; completeness is false.

```sh
git clone https://github.com/Bajtlamer/titan-gathered-forever-v3.git titan-gathered-forever
cd titan-gathered-forever
python3 tools/generate_catalog.py
python3 tools/check.py
python3 tools/package.py
```

The project's standing instruction is to install each completed, verified runtime update automatically into the local Forever client with tools/install.py, retaining backups and verifying installed bytes. This does not publish GitHub releases or change hosting.

Python 3.10 or newer and LuaJIT with Lua 5.1 semantics are required. No Git initialization is required to run these local tools. The generator reconstructs profession addon folders from `catalogue/`. Runtime Lua lives in `TitanGatheredForever/`, including its `Data/` and `Localization/` folders. Tests and tools live in root `tests/` and `tools/`. Avoid editing unrelated addons.

See [AGENTS.md](AGENTS.md) for current repository conventions and automatic local-installation instructions, [the runtime reference](ref-wow-forever-runtime.md) for implementation evidence, and [the roadmap](plans/plan-next-development.md) for outstanding work.

## Releases and website downloads

Every release must provide:

- One full collection ZIP.
- Fourteen independent ZIPs: the core, twelve profession modules and Auction Items.
- A download index with version, dependencies, filenames, sizes and SHA-256 hashes.
- Checksums for the downloadable archives.

`python3 tools/package.py` builds the normal distributions and a clean upload directory at `dist/releases/<version>/`. Upload the contents of that version directory to the website's download area. The collection ZIP installs all modules; individual ZIPs let users select only their professions. Source archives supplied automatically by GitHub are development source, not installable addon packages.

The standalone Discovery module is released on its own: `python3 tools/package.py --standalone` builds `dist/standalone/<folder>-<version>/` with the ZIP, a download index and checksums. The published collection and the fourteen ZIPs do not contain it.

Tagged GitHub releases use the same build and verification pipeline. Runtime ZIPs exclude tests, catalogue source JSON, private archives, Git metadata, development documents and unrelated addons. See [the release playbook](book-releases.md) for publishing steps.
